# Plan técnico — Operaciones de mesa recuperables

> **Pospuesto:** documento de referencia para una etapa futura, no requisito ni plan de implementación activo del prototipo universitario 001. Cualquier adopción posterior requiere revisar contratos, despliegue y aprobación antes de implementarlo.

## Compatibilidad y despliegue

- La lectura `GET /api/mesas` no cambia. El flujo recuperable sustituye las mutaciones directas de mesa/grupo para T5; los tres endpoints de mutación legados deben quedar deshabilitados con una respuesta de migración explícita `410 OPERACION_REQUIERE_PREPARACION`. No se admite fallback silencioso: permitir escrituras legadas eludiría este protocolo. Despliegue coordinado de API y Desktop; documentar incompatibilidad antes de actualizar producción y actualizar clientes HTTP/pruebas. No modificar `InitialCreate`.
- Un UUID no bloquea cambios de otros usuarios ni otras terminales. Cada ejecución revalida versiones y reglas en la API. La deduplicación ofrece como máximo una ejecución **por UUID**, no evita que otra intención humana use un UUID distinto; la concurrencia optimista y reglas de dominio mantienen su función.

## Registro y transacciones

- Crear `operacion_mesa`: UUID global PK, FK usuario restrictiva, tipo y versión de contrato, argumentos normalizados JSONB acotados y su huella SHA-256, estado (`Preparada`, `Completada`, `Rechazada`, `Cancelada`), timestamps UTC, status/código/resultado tipado y fecha de archivo. `id_instalacion` es metadato opcional no utilizado para autorizar. Campos de intención/huella admiten NULL exclusivamente para barrera `Cancelada` creada antes de preparación. Agregar CHECKs de coherencia e índices por propietario/estado/fecha.
- Preparación usa inserción condicional por PK. Si existe UUID del mismo usuario, compara representación canónica y devuelve el registro si coincide; una discrepancia devuelve 409. Un usuario distinto del propietario no puede preparar ni ejecutar el UUID, aunque sea Jefa/Supervisor; no se filtran argumentos ni estado en esos intentos. La unicidad en PostgreSQL serializa preparación/cancelación simultáneas incluso si todavía no existe fila.
- Canonicalizar a partir de DTOs validados, no JSON crudo: tipo, versión fija, enteros y estado exacto; miembros del grupo ordenados por `idMesa`, sin IDs duplicados. Limitar a 15 mesas, nombres de tipos conocidos y body máximo de 16 KiB. Guardar tanto los argumentos tipados como su huella; una huella no sustituye comparación de propietario/tipo/versión.
- Ejecución: abrir transacción, `SELECT ... FOR UPDATE` sobre la operación, revalidar propietario/rol y estado. Si está terminal, devolver el resultado guardado sin ejecutar. Si está preparada, ejecutar la regla de negocio utilizando la **misma conexión y transacción**; guardar el resultado y la auditoría y confirmar una vez. La transacción del servicio de dominio actual debe refactorizarse para poder participar en la transacción exterior, sin nested transactions ni pérdida de auditoría. Los rechazos de dominio deterministas se guardan como `Rechazada` y se confirman sin mutación. Un error interno revierte todo y no inventa un rechazo terminal.
- Antes de registrar un rechazo por excepción de concurrencia EF/PostgreSQL, volver a un savepoint válido o revertir la transacción; no intentar confirmar una transacción abortada ni registrar rechazo fuera de una barrera de concurrencia sin recuperar el lock de operación. Diseñar/probar los casos de fallo durante el commit: ante resultado desconocido, consultar UUID, nunca inferir rollback.
- **Estrategia inicial de conflicto EF:** crear savepoint después de bloquear y validar la operación y antes de tocar entidades de negocio. Ante `DbUpdateConcurrencyException`, volver al savepoint, descartar todos los cambios rastreados del dominio y auditoría, recargar explícitamente la operación dentro de la misma transacción y comprobar que sigue bloqueada y `Preparada`; solo entonces registrar el rechazo de concurrencia. Si el rollback o limpieza falla, abortar toda la transacción y no registrar terminal. No usar un contexto separado que confirme el rechazo mientras la transacción de negocio siga incierta. S3/S4 deben probar que ningún `SaveChanges` posterior persiste entidades residuales. Cualquier excepción no clasificada revierte todo; una resolución ambigua del commit se consulta por UUID.
- Cancelación: insertar barrera `Cancelada` si UUID no existe; si existe, adquirir `FOR UPDATE`. Si sigue preparada, convertir a terminal `Cancelada`; si ya es terminal, devolver el estado existente. El lock serializa la carrera con ejecución. Una solicitud bloqueada que vence no implica que el cancelado se haya aplicado. Preparación tardía para una barrera cancelada nunca ejecuta ni sustituye su propietario.
- La cancelación solicitada por Jefa/Supervisor de una operación ajena o UUID todavía inexistente crea `OperacionMesaCancelada` en auditoría con UUID, actor, propietario si existe y resultado, en la misma transacción que establece la barrera. Si el UUID aún no existe, la marca tiene como propietario al actor que crea la barrera; no se inventa un propietario original, pero el registro local conserva su identidad para mostrar la situación. La preparación tardía del usuario original se rechaza. La autorización supervisada no permite ejecutar ni cambiar la intención ajena. Repetir una cancelación terminal no genera otro evento de cancelación exitosa; si la operación ya estaba completada/rechazada, se devuelve el resultado real sin registrar una cancelación inexistente.
- Las consultas GET usan lectura normal; durante ejecución no confirmada pueden mostrar `Preparada`. Solo la resolución terminal es concluyente. No publicar `En ejecución` si no se dispone de un mecanismo persistente y consistente para ese estado.

## Contratos HTTP

Todos requieren JWT/sesión vigentes. Preparación y ejecución exigen propietario y roles de modificación; consulta/cancelación permiten al propietario autenticado incluso si su rol cambió, o a Jefa/Supervisor con rol vigente. Cocina no puede preparar ni ejecutar ni recuperar operaciones ajenas. Un usuario desactivado o sin sesión no puede operar.

- `PUT /api/operaciones/{uuid}`: body tipado con `tipo`, `versionContrato: 1` y `argumentos`. Para mesa: `{ "tipo":"CambiarEstado", "versionContrato":1, "argumentos":{"idMesa":1,"estado":"Ocupada","version":42} }`; creación: `tipo: "CrearGrupo"`, argumentos `{ "mesas":[{"idMesa":1,"version":42},{"idMesa":2,"version":43}] }`; cierre: `tipo: "CerrarGrupo"`, argumentos `{ "idGrupo":1 }`. Primer registro 201; registro propio idéntico 200; argumentos inválidos 400 `VALIDATION_ERROR`; misma clave propia distinta 409 `OPERACION_CLAVE_EN_USO`; clave de otro usuario 404 `OPERACION_NO_ENCONTRADA`.
- `GET /api/operaciones/{uuid}`: 200 con `{ "idOperacion", "estado", "resultadoArchivado", "resultado" }`; resultado terminal detallado `{ "status", "code", "data" }`, donde `data` contiene DTO de mesa/grupo o null para 204. Si fue archivado, `resultadoArchivado: true`, `resultado: null`; el estado terminal permanece. Inexistente o no autorizado 404 `OPERACION_NO_ENCONTRADA`; Jefa/Supervisor pueden consultar una operación ajena. El cliente no considera 404 prueba de cancelación.
- `POST /api/operaciones/{uuid}/ejecucion`: sin body. Para un resultado guardado, devuelve 200 con la misma representación de GET; `resultado.status` conserva el status original de dominio (200/201/204 o 4xx) y `code` su código estable. UUID ajeno/inexistente 404; estado `Cancelada` no ejecuta y devuelve su representación terminal. Errores de autenticación y transporte conservan status HTTP normales.
- `POST /api/operaciones/{uuid}/cancelacion`: sin body; crea barrera si es inexistente o devuelve estado terminal/preexistente, siempre 200 con representación. UUID ajeno devuelve 404 salvo para Jefa/Supervisor. La creación de una barrera sin preparación requiere el rol de modificación, para limitar abuso; un propietario cuyo rol cambió puede cancelar su propia operación existente. La cancelación supervisada se confirma y audita como indica la sección de transacciones.
- Errores propios de protocolo usan `application/problem+json`, `status`, `code`, `traceId`; límites y formato UUID inválidos se rechazan antes de persistir. Resultado de dominio dentro de la representación no expone excepciones, datos ajenos ni secretos.

## Persistencia y recuperación Desktop

- Antes de preparación, persistir atómicamente en disco UUID, identificador del usuario propietario, fase local y versión de formato; no guardar credenciales, tokens ni body de la intención. La intención se mantiene en memoria solo hasta enviarla. Ubicación por instalación en ProgramData con ACL explícitas y separación de configuración/logs; proteger integridad/archivo parcial y exclusión mutua entre procesos, y fallar cerrado si no puede persistirse o recuperarse el registro. No modificar `desktop.json` ni regenerar identificadores.
- **Provisión del diario:** el instalador crea `%ProgramData%\ElCarbonazo\recovery\journal.json` válido, con versión e `idInstalacion` coincidente y estado explícito `SinPendientes`, antes del primer uso o actualización coordinada. El archivo existe siempre, incluso tras resolver; Desktop actualiza atómicamente su estado y nunca lo elimina ni crea uno vacío cuando falta. Directorio y archivo permiten lectura/escritura solo a identidades operativas autorizadas y administradores; configuración permanece separada y de solo lectura. Verificar ACL efectivas y comportamiento de reemplazo atómico en Windows con dos cuentas y procesos. Si falta, está corrupto, su UUID no coincide o no se puede asegurar exclusión/persistencia, bloquear mutaciones y orientar a administrador; nunca restaurar automáticamente `SinPendientes`. El instalador no sobrescribe un diario existente en actualización/reparación. Si se perdió, restaurar exclusivamente desde copia íntegra verificada o mantener bloqueo hasta que exista un procedimiento administrativo posterior que demuestre resolución; no basta crear archivo vacío.
- Esta protección cubre fallos accidentales bajo ACL correctamente configuradas, no manipulación intencional por una cuenta con permisos de escritura ni por administrador. No se afirma que checksum o doble archivo detecten borrado/restauración coordinados o un backup obsoleto; no restaurar un diario antiguo como prueba de que no hay operación pendiente.
- Si se pierde la respuesta de preparación y Desktop se reinicia sin intención en memoria, consulta UUID; si no existe o está preparado, solicita cancelación para crear la barrera definitiva. Reintentos de preparación solo son posibles mientras se conserva exactamente la intención en memoria; no se reenvía una escritura de negocio automáticamente.
- La recuperación automática solo consulta y reconcilia; no ejecuta automáticamente una intención preparada tras reinicio. Si es necesario resolverla, el usuario propietario puede cancelar, esperar terminal y confirmar una intención nueva. Tras resultado terminal, hacer GET de mesas; borrar el registro local solo después de mostrar resultado y completar reconciliación. Resultado archivado requiere consulta y comunicación explícita al usuario.
- Si un usuario diferente inicia sesión en la misma terminal, mantener bloqueadas las mutaciones de esa terminal hasta resolución terminal y GET. Jefa/Supervisor pueden consultar el UUID y solicitar cancelación explícita; no pueden ejecutar la intención ajena. Otros usuarios reciben orientación para contactar a Jefa/Supervisor sin revelar argumentos. Esto no bloquea otras terminales. La recuperación supervisada no elimina registros locales hasta obtener resultado terminal y reconciliar.
- La consulta automática de operación usa el mismo canal de polling de sesión, sin generar actividad ni refresh. Si el token vence, entra en `Paused`; la recuperación se reanuda tras interacción humana y refresh exitoso.

## Retención, límites y pruebas

- Retener detalle terminal 30 días como valor inicial configurable, nunca menos; la compactación a marca permanente es un procedimiento administrativo documentado, no una purga automática en esta entrega. Conservar UUID, propietario, huella opcional, estado, fecha y marcador archivado. No eliminar marcas ni operaciones preparadas; monitorear crecimiento y respaldos.
- Como límite inicial de protección, admitir hasta 30 preparaciones nuevas por usuario y minuto, sin cola; devolver 429 con `Retry-After` y `ProblemDetails` cuando se exceda. Repetir una preparación existente idéntica no consume el cupo de creaciones. Consulta, ejecución de UUID existente y cancelación no comparten ese límite para no impedir recuperación; se sujetan a autenticación y autorización. Un eventual límite adicional requiere pruebas que demuestren que la recuperación y la barrera de cancelación no quedan bloqueadas. Desktop admite una sola operación local pendiente por terminal.
- **Cupo transaccional:** ventana fija UTC de 60 s según reloj de PostgreSQL; una fila de contador por usuario, con inicio de ventana y conteo, se crea y bloquea `FOR UPDATE` en la misma transacción de preparación. Orden fijo para preparación: contador de usuario → inserción condicional de UUID; cancelación y ejecución nunca toman el contador, evitando inversión de locks. Tras adquirir el contador, intentar insertar operación con `ON CONFLICT DO NOTHING`; solo si la inserción realmente ocurre y aún hay cupo se incrementa el contador y se confirma la fila. Si el cupo está agotado, revertir la inserción y responder 429; una colisión se resuelve con lectura, autorización y comparación sin consumir cupo, incluso cuando ya se alcanzó el límite. La espera de un UUID en conflicto no autoriza ejecutar. Si se revierte la transacción tampoco se consume cupo. `Retry-After` se calcula con techo en segundos hasta el fin de la ventana; reinicio de API no reinicia el contador. S2/S4 deben probar límite y duplicados concurrentes usando conexiones independientes.
- Pruebas PostgreSQL temporal: carreras de dos preparaciones y preparación/cancelación, cancelación antes de llegada, ejecución/cancelación, ejecución simultánea, caída antes/después de commit, fallos de auditoría y conflictos EF, expiración de sesión y roles, aislamiento de usuarios, archivo y solicitudes tardías. Verificar que nunca se ejecuta dos veces ni se devuelve resultado terminal contradictorio.
- Pruebas Desktop con servidor/reloj falsos: persistencia fallida y reinicio en cada fase, respuesta perdida, cancelación de UUID inexistente, operación de otro usuario, TLS, token pausado, lectura antigua, reconciliación y ninguna ejecución automática offline. Revisión visual manual en T6.
