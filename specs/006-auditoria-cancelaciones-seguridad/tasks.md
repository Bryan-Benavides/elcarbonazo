# Tareas propuestas 006 — Auditoría, cancelaciones y seguridad

**Estado: reanudado por autorización explícita del usuario para el perfil universitario local.** El flujo de anulación se implementó de extremo a extremo en API y Desktop, se provisionó el diario local y se ejecutó un recorrido REST real contra PostgreSQL temporal. **No se declara aceptación integral ni aptitud de producción:** siguen pendientes carreras con Caja/KDS/envío, TTL/cardinalidad HMAC, compatibilidad de huellas Caja y revisión visual/LAN. El módulo de reservaciones de la defensa no se ve afectado; este 006 es el de auditoría, cancelaciones y seguridad autorizado ahora.

**Reanudación y evidencia local:** `AnulacionCoordinator` captura la generación de sesión antes de registrar el diario, exige esa generación en autorización/ejecución/barrera y no reejecuta ante incertidumbre; `AnulacionApiService` emite una sola vez sin refresco ni reintento; el ViewModel serializa polling, envío y anulación con el mismo semáforo y revalida la cuenta antes de confirmar. El diario `recovery\anulaciones` se crea explícitamente con `--aprovisionar-diario-anulaciones` y `scripts/instalar-diario-anulaciones.ps1`, con ACL restringida y sin reparación automática. La consulta/barrera de una operación resuelta devuelve 200 y `CuentasService` oculta líneas anuladas del salón. Se añadieron pruebas de coordinador y ViewModel, y `--anulaciones-smoke` verificó por REST autorización, ejecución, replay terminal, consulta, filtrado de cuenta y barrera durable. El diario real quedó provisionado en este equipo. Regresión: formato/build correctos, **165 pruebas API y 288 Desktop** aprobadas, auditoría NuGet sin vulnerabilidades reportadas. Ver `docs/validacion-006.md`.

**Límites que mantienen el 006 abierto para producción:** no se probaron carreras reales con Caja prepare/execute, KDS, envío o ajuste; ni token expirado/revocado o replay concurrente; ni el umbral de cinco fallos, el límite/TTL de 100 pares HMAC; ni huellas Caja v1/v2 o cobro de una cuenta parcialmente anulada; ni render, contraste, teclado o LAN física. El diario es local a esta instalación Windows, no una barrera distribuida.

**Historial previo:** se conserva el trabajo y la evidencia de las secciones siguientes. Las cifras de regresión anteriores corresponden a sus fechas y no al estado actual.

**Avance parcial C2:** el envío guarda snapshots por línea/ingrediente en su transacción; 9 pruebas focalizadas verificaron, entre otros casos, líneas repetidas, replay, rollback y carrera con reemplazo de receta. No se ha implementado la anulación ni sus barreras; ninguna tarea integral de C2 se considera cerrada. Ver `docs/validacion-006.md`.

**Recuperación parcial posterior:** se añadió un servicio no expuesto por HTTP para consultar o establecer una barrera durable bajo advisory lock propio de 006, con sesión/rol comprobados tras el lock, intervención ajena explícita y auditada, y conservación de resultados terminales. Tres pruebas focalizadas PostgreSQL cubren barrera idempotente/concurrente, sesión revocada, preservación de resultado y rollback ante fallo de auditoría. Todavía no existen las rutas de autorización y ejecución que deben compartir el lock, ni se han probado sus carreras: esto no completa la recuperación ni habilita anulación funcional.

**API C2 — avance adicional, aún incompleto:** se añadió `POST /api/seguridad/autorizar-anulacion`, que comprueba sesión, Jefa activa y contraseña sin crear sesión nueva; vincula el UUID a una intención canónica y persiste solo el hash SHA-256 de un token aleatorio con expiración máxima de 120 s. La validación se ejecuta dentro de `HmacAutorizacionGuard`; se agrega el contador separado por solicitante/par HMAC y auditoría sin correo ni credencial. Una prueba temporal comprobó emisión, vinculación y almacenamiento hash. También se agregaron rutas para listar/acuse de alertas KDS pendientes. **No existe aún endpoint/servicio de ejecución de anulación**, por lo que no se conectó autorización a efecto de negocio y las alertas no se generan por el negocio. Faltan pruebas de fallos/umbral, cardinalidad y TTL de claves, consumo único, operaciones y barrera compartiendo lock, endpoints de auditoría, reversión, Caja/KDS integral y concurrencia. Ninguna tarea de C2 se marca completa.

**API C2 — ejecución integrada parcial:** se añadió `POST /api/pedidos/{idPedido}/anulaciones`, terminal durable, comprobación de token con comparación constante, lock UUID compartido con autorización/recuperación, barrera global de Caja, validación de snapshots contra el kardex agregado, suma acumulada de reversiones bajo locks, actualización de stock/versiones, detalle/comanda/pedido, alerta y auditoría en una transacción HMAC protegida. Los rechazos de dominio se guardan terminalmente mediante savepoint; la repetición devuelve resultado terminal. Se exponen GET/POST de consulta y barrera de operación. Caja ahora calcula/copia líneas activas; Cocina oculta detalles cancelados y agrega estado solo desde comandas con líneas activas; envío bloquea la reapertura de un grupo con pedido cancelado hasta cierre explícito. Una prueba PostgreSQL temporal cubre flujo de autorización→anulación total→reversión→alerta, rollback íntegro ante fallo de auditoría, replay terminal, consulta/acuse KDS individual y consulta de historial. Regresión observada antes de estas últimas ampliaciones: 159 API, 262 Desktop, formato/build y auditoría NuGet aprobados.

**C2 sigue incompleto y no se declara aceptado:** el e2e ahora cubre anulaciones de línea consecutivas sobre una misma comanda, reversión limitada al snapshot restante y cambios de estado solo al cancelar la última línea. Falta cobertura concurrente, carrera determinista contra Caja prepare/execute y KDS/envío/ajuste, autorización expirada/revocada y replay concurrente, TTL/cardinalidad de pares (incluido el límite de 100) y compatibilidad de huellas Caja v1/v2. No cubre aún todos los órdenes de carrera ni la integración HTTP completa. No se aplicaron migraciones persistentes.

**C3 — avance parcial:** Cocina Desktop consulta alertas con cursor opaco y acusa un evento mediante transporte de una sola emisión; la vista distingue «ANULADO — NO PREPARAR» y el acuse queda limitado al evento. Se añadió `AnulacionJournal`, independiente del de Caja, con estados pendiente/terminal/conciliado, almacenamiento mínimo y fallo cerrado si falta o es inválido, más provisionador Windows explícito no invocado al inicio. Pruebas cubren persistencia/reinicio, exclusión de secretos y no reparación. El diario aún no está cableado al arranque ni a un coordinador de recuperación; falta prueba ViewModel de incertidumbre/alertas, modal y cliente del flujo de anulación, auditoría Desktop y revisión visual real. No se inicia una escritura de anulación desde Desktop.

Regresión posterior a la prueba de líneas consecutivas y al diario: **159 API y 265 Desktop** aprobadas, `dotnet format --verify-no-changes`, build y auditoría NuGet correctos. C2/C3/C4 siguen abiertos; esto no equivale a aceptación integral.

**Límites de C1:** la FK RESTRICT de autorización conserva su sesión; la limpieza actual solo borra historial de refresh, no sesiones. Las FKs compuestas no prueban el consumo acumulado: requiere controles y pruebas transaccionales de C2. No se ha implementado cancelación funcional. Ver `docs/validacion-006.md`.

**Bloque adicional:** se endurecieron los CHECK de resultados terminales y motivo y se agregaron triggers de transición terminal y de consumo/acuse único, probados en PostgreSQL temporal; el usuario aprobó espera durable de 24 horas ante cambio no coordinado de clave HMAC. **Avance posterior:** la migración 006 agrega FKs compuestas que rechazan anulaciones con comanda/pedido o detalle/comanda discordantes y reversiones con destino distinto de la anulación; pruebas PostgreSQL ejercitan esas violaciones.
